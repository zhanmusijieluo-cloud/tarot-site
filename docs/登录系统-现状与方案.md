## 三、三个硬伤

### 硬伤 1 ⚠️⚠️⚠️ 邮件每小时只能发 2 封

Supabase 免费版用的是**内置邮件服务**，官方限流：

> **2 emails per hour** with the built-in email provider.
> — Supabase Docs, Rate limits

**这意味着什么**：一天最多约 48 封。而以下操作全部消耗邮件配额：

- 新用户注册 → 验证邮件
- 用户忘记密码 → 重置邮件
- 用户没收到 → 重发（我代码里留了 60 秒倒计时，但配额是全局的）

**只要同时有 3 个人注册，第 3 个人就会失败。** 这不是"以后优化"的问题，是上线即崩。

**必须做的**：接一个自定义 SMTP，把 Supabase 的邮件发信切过去。

### 硬伤 2 只有邮箱一种登录方式

目前用户想登录，**只能**用邮箱注册 + 收验证邮件。

对你的目标用户来说这有明显摩擦：

- **日本用户**：LINE 几乎是默认通讯工具，不用邮箱注册是常态
- **中文用户**：习惯微信/手机号一键登录，让填邮箱会掉一批
- **专业塔罗师**：可能同时管理多个平台，更在意"能不能快速进后台"

### 硬伤 3 服务端拿不到登录态

现在会话存在浏览器 localStorage，服务端完全不知道用户登没登录。后果：

| 做不到的事 | 影响 |
|---|---|
| 服务端渲染时判断登录态 | 账户页必然先闪一下"未登录"再变已登录 |
| 用 cookie 保护 API 路由 | `/api/*` 无法识别用户身份，只能靠前端传 token |
| 服务端重定向未登录用户 | 未登录也能打开 `/account`（只是页面内提示） |
| SEO / 首屏体验 | 账户类页面无法做服务端渲染 |

现在**不算 bug**（账户中心本来就是客户端方案），但如果后面要做「服务端生成的个性化内容」或「API 级鉴权」，就必须先解决这个。

## 四、可选方案

### 4.1 邮件通道 —— 必做，优先级最高

| 方案 | 免费额度 | 优点 | 代价 / 注意 |
|---|---|---|---|
| **Resend** ⭐推荐 | 3,000 封/月，100 封/天 | 开发者体验最好，Supabase 官方文档主推；接入只要填 SMTP 参数 | 要在域名 DNS 加 SPF/DKIM 记录 |
| **Brevo**（原 Sendinblue） | 300 封/天 | 额度大 | 控制台偏营销工具，稍重 |
| **SendGrid** | 100 封/天 | 老牌稳定 | 免费版审核较严，国内访问偶尔不稳 |
| **阿里云邮件推送 / 腾讯云 SES** | 按量付费，很便宜 | 国内送达率好 | 域名需备案；面向日本用户送达率一般 |
| **Supabase Send Email Hook** | 无限制 | 可以完全自定义发信逻辑（比如走自己的服务） | 要自己写一个发信端点，工作量最大 |

**我的建议**：先用 **Resend**。你的域名 `mustar.vip` 加三条 DNS 记录就能用，免费额度对早期完全够。等量大了再换。

> 📌 这里需要你确认：**域名 `mustar.vip` 的 DNS 在哪管理？**（Vercel / Cloudflare / 域名商）——决定加 DNS 记录的入口在哪。

### 4.2 登录方式 —— 可多选，按性价比排序

| 方式 | 覆盖人群 | 接入难度 | 说明 |
|---|---|---|---|
| **邮箱 + 密码**（已有） | 通用 | — | 保留，作为兜底 |
| **Google 登录** | 全球通用 | ⭐ 低 | Supabase 原生支持，后台点开 + 填 Client ID/Secret 即可 |
| **Apple 登录** | iOS 用户 | ⭐⭐ 中 | 原生支持；但需 Apple 开发者账号（$99/年） |
| **LINE 登录** | **日本主力** | ⭐⭐⭐ 高 | ⚠️ **Supabase 没有内置 LINE provider**，需走 Custom OIDC 或自建回调 |
| **微信登录** | 中文用户 | ⭐⭐⭐⭐ 很高 | Supabase 完全不支持，需自建整套 OAuth 流程；且需企业主体 + 备案 |
| **手机号 + 验证码** | 通用 | ⭐⭐ 中 | Supabase 原生支持，但短信要接 Twilio/阿里云，**按条计费**（国际短信约 ¥0.3~1/条） |
| **Passkey / 指纹** | 尝鲜用户 | ⭐⭐ 中 | Supabase 已支持（当前关闭）。无密码登录，体验好但用户认知度低 |

**我的建议（分批）**：

1. **第一批**：Google 登录。成本最低、覆盖最广，能立刻降低注册摩擦。
2. **第二批**：**LINE 登录**。如果你的主力市场是日本，这个的优先级其实比 Google 还高——日本用户不用邮箱注册是常态。但要注意 Supabase 不原生支持，要单独做。
3. **第三批**：手机号验证码。等有收入了再说，短信是持续成本。
4. **微信登录**：如果目标是国内市场，绕不开，但工作量和资质门槛都最高，建议放到明确要做国内市场时再启动。

> 📌 需要你定：**主力市场到底是日本、中文区，还是都要？** 这直接决定先做 LINE 还是 Google。

### 4.3 会话架构 —— 要不要迁到 cookie

| 方案 | 改动范围 | 得到什么 | 失去什么 |
|---|---|---|---|
| **A. 保持现状**（localStorage） | 不动 | 零成本，现在就能用 | 服务端永远不知道登录态；无法做 SSR 鉴权和 API cookie 鉴权 |
| **B. 迁到 `@supabase/ssr` + cookie** | 中：改 `supabase.ts`、加 `middleware.ts`、改登录/账户页取 session 的方式 | 服务端可鉴权、可保护路由、可做 SSR 个性化、API 能识别用户 | 需要一次性改造，且要回归测试所有已登录场景 |

**我的建议**：**先不动**。账户中心现在是纯客户端方案，能跑；等你确定要做「服务端个性化」或「API 需要识别用户」（比如积分扣减接口）时，再一次性迁移。现在迁移属于提前优化。

> 📌 需要你定：**近期有没有"服务端必须知道用户是谁"的需求？**（比如扣积分、生成带用户信息的页面）有的话就现在迁。

---

### 4.4 注册摩擦 —— 邮箱确认要不要关

当前 `mailer_autoconfirm: false`，注册必须收邮件验证。

| 选项 | 效果 | 风险 |
|---|---|---|
| **保持开启**（现状） | 邮箱真实性有保证，能发营销邮件 | 每多一步就掉一批用户；且强依赖邮件通道 |
| **关闭确认**（`mailer_autoconfirm: true`） | 注册即登录，零摩擦 | 会有假邮箱；但对你这种工具型站点风险不大 |

**我的建议**：**等邮件通道（4.1）接好之后再决定**。如果邮件通道稳，保持验证也没问题；如果发现注册转化率低，再关。
